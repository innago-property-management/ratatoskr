SQLite vs JSON Files: SQLite is probably wrong as the default The design says "zero-dep" but then reaches for \`sqlite3\` with \`asyncio.to_thread()\` wrapping. Let me challenge this hard. **What SQLite buys you:** Query capability (ORDER BY last_used_at, DELETE WHERE schema_hash = ..., COUNT). **What you actually need:** Load all recipes for an (api_id, schema_hash) pair on startup. Save one recipe. Delete all recipes for a pair. That's it. There's no ad-hoc querying here — the LRU dict is the query engine. **The JSON-lines alternative:** - One file per \`(api_id, schema_hash)\` pair: \`~/.cache/ratatoskr/recipes/{api_id_hash}/{schema_hash}.jsonl\` - Load = \`open().readlines()\` → \`json.loads()\` each line - Save = \`open("a").write(json.dumps(recipe) + "\\n")\` - Delete = \`os.remove(file)\` - Atomic writes via \`tempfile\` + \`os.rename()\` **Why this matters:** - SQLite has WAL mode footguns in containerized environments (shared volumes, NFS mounts, read-only filesystems with writable overlays) - SQLite's \`asyncio.to_thread()\` wrapper adds a thread-pool dependency for what is fundamentally a "read N small blobs" operation - JSON files are debuggable with \`cat\`. SQLite requires tooling. - For 64 recipes max, the "query capability" argument is solving a problem that doesn't exist **My recommendation:** JSON-lines as default, SQLite as an optional upgrade. Or if you insist on SQLite, at least document the WAL-mode container gotchas prominently. **Counter-argument I expect:** "SQLite is battle-tested and handles concurrent writes." True, but you have an \`asyncio.Lock\` on the RecipeStore already. There are no concurrent writers to the persistence layer — it's write-through from a single lock-protected code path. --- ## 2. Startup Load: Eager is a trap The design says "On startup: \`backend.load()\` pre-populates the in-memory LRU." **Problem 1 — Load WHAT?** The backend stores recipes keyed by \`(api_id, schema_hash)\`. At startup, you don't know which APIs the user will target. Do you load ALL recipes for ALL api_ids? That defeats the per-API schema hash invalidation — you'll load recipes for schema hashes that are now stale, and you won't know until the first request fetches the current schema. **Problem 2 — Startup latency.** If someone has 64 cached recipes across 12 different APIs, you're now blocking server startup on disk I/O. For a zero-config MCP server that's supposed to "just start," this is a regression. **Problem 3 — Memory waste.** Loading recipes for APIs that won't be used this session wastes the LRU budget. Recipe slots occupied by stale entries displace new ones. **My recommendation:** Lazy-load per \`(api_id, schema_hash)\` on first request. When the orchestrator fetches the schema and computes the hash, THAT is when you know which recipes are valid. Load them then. This also naturally handles schema invalidation — if the hash changed, you don't load the old recipes. **The design even acknowledges this** in Open Question #2 but doesn't resolve it. The eager approach in the integration section (step 2) contradicts the "schema hash = invalidation key" principle because you can't validate hashes at startup. --- ## 3. RecipeBackend Interface: Too narrow, and the wrong abstraction boundary The ABC has three methods: \`load(api_id, schema_hash)\`, \`save(api_id, schema_hash, recipe)\`, \`delete_by_schema(api_id, schema_hash)\`. **What's missing:** **3a. No \`list_all_keys()\` or \`get_stats()\`.** If you ever want to build a management UI, health check, or even log "loaded N recipes from M APIs" at startup, you can't. The interface is write-only from an observability perspective. **3b. Recipe identity is wrong.** The \`save()\` method takes \`Recipe\` (which is a plain dict) but recipes have rich metadata in \`RecipeRecord\`: \`recipe_id\`, \`tool_name\`, \`question\`, \`question_sig\`, \`question_tokens\`, \`created_at\`, \`last_used_at\`. Are you persisting the raw dict or the full record? The design is ambiguous. If you only persist the dict, you lose the fuzzy matching metadata. If you persist the full record, the interface signature should say \`RecipeRecord\`, not \`Recipe\`. **This is the critical gap.** The \`RecipeStore\` uses \`RecipeRecord\` with 10+ fields including pre-computed fuzzy tokens. The backend interface uses bare \`Recipe\` dicts. Who is responsible for reconstituting the \`RecipeRecord\` on load? The store? Then the store needs the original question text, which the backend must also persist. The interface doesn't model this. **3c. No bulk operations.** \`save()\` takes one recipe. Startup load returns a list. But there's no \`save_batch()\` for potential future migration tools, export/import, or the Redis pipeline optimization you'll inevitably want. **3d. Future extensibility for semantic matching.** The design says "not building it" but asks if the interface should support it. My answer: **no, but for the opposite reason than you'd expect.** Semantic matching would need \`search(query_embedding, top_k)\` — a fundamentally different retrieval pattern that wouldn't fit this CRUD interface anyway. Don't try to future-proof; you'll redesign the interface when you add semantic search regardless. What you SHOULD do is make sure \`RecipeRecord\` (not \`Recipe\` dict) is the persistence unit, so you have the \`question\` text available for future embedding. --- ## 4. Are We Over-Engineering This? **Yes. But not in the way you think.** The ABC + 3 backends + config + 13 complexity points is over-engineering for a 64-slot cache. But the REAL over-engineering is the Redis backend. **Who is the Redis backend for?** The design says "production deployments." But ratatoskr is a single-tenant MCP server. Who's running a Redis cluster next to their MCP proxy? If they have Redis, they probably have a proper API gateway. The Redis backend is solving an imaginary use case inspired by Cygnus (which is a multi-tenant supervisor with legitimate distributed state needs). **My recommendation:** Ship SQLite (or JSON-lines) only. Add Redis when someone actually asks for it. The ABC makes it trivially extensible later — that's the whole point of the abstraction. The current \`_recipes_equivalent()\` does structural comparison, but there's no schema validation on the \`Recipe\` dict itself. **Specific attack:** User A runs ratatoskr against a benign API, recipes are persisted. Attacker modifies \`recipes.db\` (or \`recipes.jsonl\`) to include a recipe with a SQL injection in \`sql_steps\`. User restarts, recipes are loaded, attacker's recipe is exposed as an MCP tool. **Mitigation needed:** Validate loaded recipes against the same schema used during extraction. Schema hash collision.** Recipes are keyed by SHA256 of the schema. Schema changes invalidate recipes. But what if two different schemas produce the same hash? Astronomically unlikely with SHA256, but the invalidation logic should be "hash changed → delete old" not "hash matches → assume valid." The current design is correct here, but the implementation needs to compare hashes, not assume equality means the schema is unchanged. **5e. ^D\]0;PID: 87979 | alias clc="claude -c\## Security Engineer — Delphi Panel Review ### Recipe Persistence Design: Threat Model & Security Assessment --- ### 1. SQLite vs JSON Files — Security Perspective **SQLite is the correct default.** JSON files are worse from every security angle: - **Atomic writes**: SQLite gives you ACID. JSON file writes can be interrupted mid-flush, leaving corrupted state. A corrupted recipe file that fails to parse on startup is a denial-of-service on the recipe cache. - **Path traversal surface**: JSON-per-recipe means filenames derived from \`api_id\` or \`recipe_id\`. Any slug that escapes sanitization (e.g., \`../../etc/cron.d/evil\`) is a write primitive. SQLite: one file, one path, no filename derivation from user-influenced data. - **Concurrent access**: Multiple processes writing to the same JSON file = race conditions. SQLite's WAL mode handles this. - **Query capability isn't the point** — integrity and atomicity are. SQLite is the right call. **One concern**: The proposed path \`~/.cache/ratatoskr/recipes.db\` expands \`~\` at runtime. In containerized deployments, \`HOME\` may be unset or \`/\`. Recommend: - Use \`RECIPE_SQLITE_PATH\` with a fallback chain: env var → \`$XDG_CACHE_HOME/ratatoskr/\` → \`$HOME/.cache/ratatoskr/\` → temp directory with warning - **Validate the resolved path is writable at startup**, not on first save --- ### 2. Startup Load: Eager vs Lazy — Security Perspective **Eager load, but bounded.** Lazy loading creates a timing oracle: an attacker probing different \`(api_id, schema_hash)\` combinations can observe latency differences between cache-hit (memory) and cache-miss (disk I/O). This leaks information about which APIs have cached recipes. More critically, lazy loading means the first request to a "cold" API pays the I/O penalty during the request path. Under load, this creates unpredictable latency spikes — a reliability concern that becomes a security concern if it triggers timeouts or retries that amplify load. **Recommendation**: Eager load on startup, but: - Cap at \`RECIPE_CACHE_SIZE\` (already planned via LRU) - Set a **startup timeout** (e.g., 5s). RecipeBackend Interface — Security Design Review The ABC is clean but missing one critical method: \`\`\`python @abstractmethod async def health_check(self) -> bool: """Verify backend is reachable and functional.""" \`\`\` Without this, the readiness probe (\`/ready\`) can't distinguish "SQLite file got deleted" from "everything's fine." The server reports ready but silently drops all persistence. **Interface extensibility for semantic matching / MemRL:** The current \`load(api_id, schema_hash)\` signature returns \`list\[Recipe\]\` keyed by exact match. Semantic matching would need: \`\`\`python async def search(self, api_id: str, query: str, k: int = 3) -> list\[tuple\[Recipe, float\]\]: \`\`\` This is a fundamentally different operation. I'd recommend **not** adding it to \`RecipeBackend\` now. Semantic search belongs in a separate \`RecipeIndex\` interface — mixing exact persistence with fuzzy retrieval in one ABC violates ISP and will create awkward no-op implementations in SQLite/Redis backends. **Verdict**: The ABC is well-scoped for persistence. Here's the security argument: A 64-slot LRU cache means a busy instance with many target APIs will churn through recipes quickly. Without persistence, an attacker can intentionally poison the cache by flooding requests to different APIs, evicting valuable recipes and forcing expensive LLM re-extraction. **Persistence makes cache poisoning recoverable** — evicted recipes reload on next startup. That said, scope it tightly: - **PR A only** (SQLite + Memory). Ship RedisBackend when someone actually needs it. - Don't build the optional dependency wiring until there's demand. YAGNI applies to RedisBackend for an open-source project with zero production Redis users today. --- ### 5. Security Concerns — The Scary Part #### 5A. **Deserialization of Persisted Recipes (CRITICAL)** The design says \`recipe_json\` column stores serialized recipe data. On startup, this JSON is deserialized and loaded into memory, then **executed as API calls and SQL queries**. This is a **stored code execution path**. If an attacker can write to the SQLite file (local file access, supply chain, or a bug in the save path), they control: - GraphQL query templates → arbitrary queries against target APIs - REST paths/bodies → arbitrary HTTP requests - SQL templates → arbitrary DuckDB queries - MCP tool arguments → arbitrary tool invocations on external MCP servers **Mitigations required:** 1. **Integrity check on load**: Hash each recipe at save time (\`hmac(recipe_json, secret)\`), verify on load. Reject tampered recipes. Use a per-installation random key generated on first run and stored alongside the DB. 2. **File permissions**: Create \`recipes.db\` with \`0600\` (owner read/write only). Check permissions on startup; warn if world-readable/writable. 3. **Validate loaded recipes against the same rules as freshly extracted ones**: tool name format, param declarations, template syntax. Don't trust persisted data just because it was valid when saved. #### 5B. **SQL Injection via Persisted Templates (HIGH)** Current \`render_sql_safe()\` strips \`;\`, \`--\`, \`/\*\` from parameter \*values\*. But the **template itself** is stored in the recipe and not sanitized on load. A tampered SQLite file could contain: \`\`\`sql SELECT \* FROM data; DROP TABLE data; --WHERE name = '{{param}}' \`\`\` The template bypasses \`render_sql_safe()\` entirely because that function only sanitizes parameter substitutions, not the template body. **Mitigation**: On load, validate SQL templates against the same constraints applied at extraction time. The template body should be re-validated, not just the parameters. If \`api_id\` contains \`:\` or newlines, it can break key structure or enable Redis protocol injection in poorly configured setups. **Mitigation**: Sanitize \`api_id\` in key construction. Use a hash of \`api_id\` as the key component, not the raw value. #### 5D. **Race Condition on Schema Invalidation (MEDIUM)** The design says schema change triggers \`delete_by_schema()\` on the backend. But between "detect schema change" and "delete completes," a concurrent request could load stale recipes from the backend. With write-through + read-on-startup this is minimal, but with lazy loading it's a real window. Another angle: schema hash is SHA256 of the raw schema. If the schema source (introspection endpoint) is compromised, an attacker could serve a schema with the same hash as a previous version (hash collision — theoretically infeasible with SHA256, but worth noting the trust boundary). #### 5E. **Fire-and-Forget Write Failures (LOW-MEDIUM)** "Fire-and-forget semantics — failures logged, not raised" means if SQLite writes silently fail (disk full, permissions changed, file locked), the operator has no visibility. Recipes appear to work (in-memory) but aren't persisting. **Mitigation**: - Track consecutive write failures. After N failures (e.g., 3), emit a warning-level log and increment a Prometheus counter (\`recipe_backend_write_failures_total\`) - Consider a health check that verifies the last successful write was within a reasonable window #### 5F. **Multi-Tenant Isolation (NOT IN SCOPE BUT FLAGGING)** The agent's research confirmed: \`RecipeStore\` is a global singleton. The persistence layer inherits this. For single-tenant open-source use this is fine. **Document this explicitly** as a known limitation.
