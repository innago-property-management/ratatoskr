# Delphi Panel: Schema Reduction Design Review

**Date:** 2026-03-12
**Panel:** Systems Architect, Skeptic, Pragmatist, Security Engineer, SRE
**Panel ID:** panel-4a6990f0
**Status:** Complete (5/5)

---

## Consensus Summary

Strong convergence across all 5 panelists on major decisions, with one post-panel
correction on TOON scope (see Decision 1 addendum).

### Decision 1: TOON Scope — Panel Corrected

**Original panel verdict:** Drop TOON (unanimous 5/5).

**Post-panel correction:** The panel evaluated TOON solely as a *schema* compressor
and concluded it's inert because all protocol agents pass DSL text (not JSON) to
`reduce_schema()`. This analysis was correct for the schema pipeline but **missed
TOON's primary value proposition: compressing API *responses*.**

GraphQL and REST API responses are always JSON. These hit `truncate_for_context()`
/ `MAX_TOOL_RESPONSE_CHARS` (32k) in the executor and tool response paths. TOON's
30-45% token reduction on homogeneous JSON arrays is valuable there — that's where
the largest payloads flow through.

**Where TOON helps (missed by panel):**
- GraphQL query responses (JSON)
- REST API responses (JSON)
- Any JSON payload hitting the `MAX_TOOL_RESPONSE_CHARS` cap in `executor.py`

**Where TOON doesn't help (correctly identified):**
- Schema DSL text (not JSON — TOON skips via `json.loads()` guard)
- gRPC protobuf IDL text
- MCP tool definition DSL

**Revised verdict on TOON:** Keep the dependency. Its value is in the response
pipeline, not the schema pipeline. The `ToonLayer` in `reducer.py` is correctly
inert for schemas — that's fine. TOON integration for response compression is a
separate concern from schema reduction.

**Remaining valid concerns about `toon_format`:**
- Git-pinned beta dep is a packaging concern (Skeptic, SRE) — migrate to PyPI
  release when available, or vendor the ~200 lines
- Graceful degradation is already implemented (optional import, size-check guard)

**Action:** Keep `toon_format`. For the schema reduction feature specifically,
TOON is not part of the pipeline (keyword ranking replaces it). TOON's response
compression value is tracked separately.

### Decision 2: Keyword-Ranked Truncation as Primary — Strong Consensus (5/5)

All panelists favor **option (a): keyword-ranked truncation** as the default/primary
strategy for schema reduction. AI reduction is the optional enhancement layer, not
a requirement.

| Panelist | Position |
|----------|----------|
| **Architect** | Three-tier: configured provider → keyword-ranked → hard truncation. |
| **Skeptic** | Option (c) is a trap — feeding schema to Llama 3 8B locally produces garbage. Option (a) is undervalued as primary strategy. |
| **Pragmatist** | "This isn't even a close call." Keyword ranking is deterministic, testable, zero-dependency. AI is the bonus layer. |
| **Security** | Keyword ranking has no prompt injection surface. AI reduction creates a two-hop injection chain (schema → Haiku → agent). |
| **SRE** | Hard truncation (option b) is the *cause* of the problem. Keyword ranking is the "reliable workhorse" — zero network, zero latency, zero cost. |

**Dissent on option (c):** Skeptic and Pragmatist explicitly reject using the
configured provider for reduction. Architect supports it as tier 1. Security raises
prompt injection concerns with any AI reduction path.

**Action:** Implement keyword-ranked truncation as the default schema reduction
path. AI reduction via configured provider as an optional opt-in layer (with
sanitization on output). Hard truncation as final fallback.

### Decision 3: Orchestrator-Level Integration — Consensus (4/5)

| Panelist | Position |
|----------|----------|
| **Architect** | Orchestrator handles reduction centrally. Protocol agents pass raw schema + question via ProtocolConfig. |
| **Pragmatist** | "Orchestrator, obviously." Threading `question` through three agents is unnecessary plumbing. |
| **SRE** | Centralized = one place to instrument metrics (reduction_time, reduction_ratio, method_used). |
| **Security** | Central sanitization point is better than three separate integration points. |
| **Skeptic** | (No explicit position on this question) |

**Note:** The current codebase already threads `question` through each protocol
agent to `reduce_schema()` (REST in `schema_loader.py:382`, GraphQL in
`graphql_agent.py:313`, gRPC in `grpc_agent.py:970`). Moving to orchestrator would
mean removing these 3 call sites and adding 1 in the orchestrator. Either approach
works; the panel prefers centralized.

**Action:** Move reduction into the orchestrator. Add `question` field to
`ProtocolConfig` (or pass it alongside). Each protocol agent passes raw schema
text; orchestrator applies reduction before building the system prompt.

### Decision 4: Schema Format Mismatch — Resolved

Keyword-ranked truncation works on DSL text directly — no JSON requirement. TOON
remains available for JSON payloads in the response pipeline but is not part of
the schema reduction pipeline.

### Decision 5: Ship Keyword Ranking First — Unanimous (5/5)

All panelists agree: implement keyword-ranked truncation first, ship it, then
decide if AI reduction is needed.

| Panelist | Key Quote |
|----------|-----------|
| **Pragmatist** | "You're proposing a three-layer cake when the first layer alone solves 80% of the problem with zero new dependencies." |
| **Skeptic** | "How often does TOON alone actually prevent the Haiku call? If rarely, you've added a dependency for a warm fuzzy feeling." |
| **SRE** | "Keyword-ranked truncation is zero external dependencies, zero network, zero cost." |

## Security-Specific Findings

### Prompt Injection via Schema → AI Reducer → Agent (Security Engineer)

If AI reduction is implemented later, the reducer creates a **two-hop indirect
injection chain**:
1. Attacker controls API schema descriptions
2. Schema sent to reduction model with advisory `[BEGIN UNTRUSTED SCHEMA]` markers
3. Model output becomes trusted schema context for the primary agent

**Mitigations required for any future AI reduction path:**
- Run `sanitize_schema_text()` on AI reducer **output**, not just input
- Add structural validation: verify output parses as valid SDL/OpenAPI/protobuf
- Consider allowlisting schema elements rather than open-ended summarization

---

## SRE Operational Concerns

- **Metrics needed:** `schema_reduction_method` (keyword/ai/truncated), `schema_reduction_ratio`, `schema_reduction_duration_ms`
- **P99 latency risk:** AI reduction adds a full LLM round-trip before agent work begins. Must be opt-in with timeout.
- **Hard truncation must remain as final fallback** — never remove it, even with better strategies above it.

---

## Revised Implementation Order

Based on panel consensus + TOON correction:

1. **Phase 1:** Implement keyword-ranked truncation in `reducer.py` (score schema endpoints/fields by query keyword relevance, sort by score, truncate at character budget)
2. **Phase 2:** Integrate at orchestrator level (move `reduce_schema()` calls from 3 protocol agents into orchestrator, add `question` to `ProtocolConfig`)
3. **Phase 3:** (Deferred) AI reduction as opt-in enhancement with output sanitization
4. **Phase 4:** (Separate feature) TOON response compression — apply TOON encoding in `truncate_for_context()` / tool response paths for JSON payloads
5. **Phase 5:** Observability — metrics for reduction method, ratio, duration
